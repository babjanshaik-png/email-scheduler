PROJECT IMPLEMENTATION & ENGINEERING SUMMARY

1. OVERVIEW & SYSTEM PURPOSE
--------------------------------------------------------------------------------
Built a production-grade, high-throughput email scheduling microservice and executive 
dashboard utilizing Node.js (Express with TypeScript), Prisma (SQLite/PostgreSQL), 
BullMQ with Redis, Ethereal SMTP delivery service, and a modern Next.js 15 dark-mode frontend.

The system is designed for high reliability, idempotency, distributed rate limiting, 
zero cron job dependency, and zero-loss restart recovery.


2. ARCHITECTURAL PILLARS & KEY IMPLEMENTATIONS
--------------------------------------------------------------------------------
[A] Database-First Persistence Strategy
    - Every email scheduling request is transactionally persisted into the relational 
      database with status 'SCHEDULED' before being enqueued into BullMQ.
    - Guarantees zero job loss even if Redis is transiently unavailable or restarts.

[B] Strict Separation of Queue & Worker Architecture
    - Queue Layer (backend/src/services/queue.ts): The REST API strictly handles job 
      enqueueing and validation. It contains zero worker processing or polling loops.
    - Worker Engine (backend/src/services/worker.ts): Dedicated BullMQ worker thread 
      responsible for concurrency management, rate-limit evaluation, delayed execution, 
      idempotency verification, and exponential retry backoff.

[C] 1:1 Deterministic Job Mapping & Worker Idempotency
    - Each database record stores a deterministic BullMQ jobId (e.g. email-{id}).
    - Before sending any email, the worker verifies the current status in PostgreSQL/SQLite.
    - If status is 'SENT' or 'CANCELLED', execution is skipped cleanly, guaranteeing that 
      an email is NEVER sent more than once (protects against worker crashes or duplicate jobs).

[D] Distributed Hourly Rate Limiting & Throttling Engine
    - Implemented distributed sliding rate-limit counters in Redis keyed by 
      'rate_limit:{yyyy-mm-dd-hh}:{senderEmail}'.
    - When a sender reaches MAX_EMAILS_PER_HOUR_PER_SENDER (default: 10), jobs are NOT 
      failed or dropped. Instead, the worker calculates the exact delay until the next 
      UTC hour window and reschedules the job automatically.
    - Enforces a minimum delay between individual emails (MIN_DELAY_BETWEEN_EMAILS_MS) 
      to mimic natural ISP throttling.

[E] Zero Cron Jobs & Complete Restart Resilience
    - Operating completely without OS cron or node-cron timers.
    - Delayed jobs are naturally stored in Redis ZSETs.
    - Built a Startup Reconciliation Service (backend/src/services/reconciliation.ts) 
      that audits the database on server startup for any 'SCHEDULED' records and 
      synchronizes them with BullMQ.
